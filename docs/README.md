## 文档类型约定

| 类型 | 存放位置 | 回答什么 |
|---|---|---|
| **spec** | `docs/specs/` | 做什么、什么算做完（功能需求 FR / 成功标准 SC / 验收标准 AC） |
| **design** | `docs/designs/` | 具体怎么做（结构、算法、数据流、视觉规范） |
| **ADR** | `docs/adr/` | 为什么这么决策（含被否决的方案与理由） |
| **plan** | `docs/plans/` 或 `.harness/planning/` | 实施步骤与顺序 |

---

## 三条写法要求

1. **spec 里的 AC 必须含至少 1 条错误路径 + 1 条边界** —— 否则 Agent 只做 happy path
2. **ADR 必须写被否决的方案** —— 只写"我们选了 X"的 ADR，下次无法判断当初为什么排除 Y
3. **能写进 spec 的不要写进 design** —— 两份文档说同一件事时，必然有一份会过期

## 维护

- 新增文档**必须**在本表加一行
- 文档删除时同步删索引
- 季度修剪：合并重复文档，标注过期的（不要直接删，标 `DEPRECATED` + 指向新文档）

## 与 .harness/ 的分工

| | `docs/` | `.harness/` |
|---|---|---|
| 内容 | 产品与技术的**设计** | 工程的**治理 / 经验 / 技能 / 交付** |
| 回答 | 做成什么样 | 怎么做才不会烂尾 |
| 变化频率 | 随功能演进 | 随工程实践演进 |
| 唯一索引 | 本文件 | `.harness/README.md` |

**不重叠原则**：设计决策进 `docs/`，工程规程进 `.harness/`。
同一件事在两处都写 → 必然漂移 → Agent 遵循过期的那份。
