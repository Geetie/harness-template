## 第 ② 问：是不是真的可插拔模块化？

**结论：是真的。但抓到一个真缺陷 —— 有一条检查规则不认"模块已关闭"状态。**

### 实验 1：关模块后是否真的不留残骸

```bash
python scripts/new_project.py --name PA --preset full \
    --disable decisions,planning,skills --target <tmp>
```

| 检查 | 结果 |
|---|---|
| 被关模块（decisions+planning+skills）的 owned 文件在产物中**残留数** | **0** ✅ |
| 开启模块（7 个）的 owned 文件**缺失数** | 1（即缺陷 A 的臆想路径） |

**`config.json` 实际写入**（开关是落盘的，不是内存态）：<!-- lint-ignore -->
```json
"modules": {
  "instructions": true,  "state": true,   "verification": true,
  "memory": true,        "delivery": true,"routing": true,
  "decisions": false,    "planning": false,"skills": false,
  "placeholder-guard": true, "integration-check": true

```

### 实验 2：依赖缺失是否自动补齐且**告警**（不静默）

| 场景 | 输出 | 判定 |
|---|---|---|
| 只关 `delivery` | `delivery=False`，无告警 | ✅ 正确（它依赖的 verification 仍开着） |
| 关 `verification` | `verification=True`（被补回）、`delivery=True`，**告警 1 条** | ✅ 正确，且**打印了原因** |
| `preset=minimal` | 开着 4 个、告警 0 条 | ✅ 档位内自洽 |

告警原文：`模块 delivery 依赖 verification，已自动启用 verification（否则 delivery 缺少依赖会静默降级）`

### 实验 3：降级是否显式（不静默）

在关掉 decisions 模块的项目里跑 lint：

```
[SKIP] .harness/planning/decisions/ 不存在 → 跳过决策演进检查 (L008, L009, L010, L011)
```

✅ **显式声明了跳过原因**，而不是悄悄不检查。

### 实验 4：反向 —— 有没有"关了还在跑"的模块？

| 项 | 结果 |
|---|---|
| 被关模块的检查是否仍执行 | ✅ 不执行（决策组整组跳过） |
| 被关模块的路径是否被误判为死链 | ✅ 被豁免（L001 双面比对） |
| **被关模块被"上游模块"引用的注册项** | ❌ **仍被报 ERROR** ← 缺陷 B |

**缺陷 B 详情**：`ROUTER.md`（routing 模块，开启）里注册了 4 张能力卡，其中 3 张属 `skills` 模块（被关闭）。`L004` 只查磁盘、不查开关，于是稳定报 **3 条假 ERROR**：

```
❌ .harness/routing/ROUTER.md
    注册表引用的技能/能力卡不存在: ../skills/delivery-gate/SKILL.md
```

这正是我自己写的 `MODULES.md` **铁律④「检查规则本身必须认识"模块已关闭"状态」** 的反面教材 —— 规则写了，但只在一个地方（L001）落实了。**已修**（缺陷 B）。

### 实验 5：模板仓库自己能不能满足自己的门禁？

**不能。这是一个真问题。** 模板仓库也是 git 仓库、也跑 `.githooks/pre-commit`，但它的：
- `.harness/state/progress.md` —— 是**要被复制出去的脚手架**，必须保持未填写
- `.harness/memory/lessons.md` —— 同上

门禁强制"代码变更必须同步这两个文件"，于是模板**只能靠污染自己的脚手架才能提交**（第一次尝试提交就被拦下了）。

→ 已修（缺陷 E）：新增 `.harness/TEMPLATE-REPO` 标记 + pre-commit **模板仓库模式**。

夹具：一份文档，同时包含①代码块内示例 ②真声明（依赖已失效 ADR-001）③真声明（依赖有效 ADR-002）

### 审计过程中最值得记录的一次"自我打脸"

验证缺陷 C 时，我第一版夹具用了**相对路径**，结果：

- 所有检查函数静默跳过
- 输出 `0 findings`
- 界面显示"✅ 未发现漂移"

而真实调用链传的是 `collect_docs` 产出的**绝对路径**。
**测试结论对，测试过程骗人。** 这正是 M0「假成功」本身 —— 一个审计工具差点因为同一个陷阱给出假的"通过"。

→ 固化为 **S14**（读文件失败被静默吞掉 = 检查器整体空转）+ **P24**（换一种输入写法，就要重做一遍对照）
