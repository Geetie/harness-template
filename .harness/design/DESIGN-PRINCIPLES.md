# 设计原则与模式选择

> **定位**：给 Agent 在**写代码之前**用的判断依据，不是事后 checklist。
> 与 `.harness/planning/SPEC-TEMPLATE.md` 的「设计决策四问」配套使用。

---

## 0. 先说清楚：机器能查什么、不能查什么

这是本文件最重要的部分，**别搞错杠杆点**：

| | 能机器检查吗 | 例子 |
|---|---|---|
| **技术债信号（smell）** | ✅ 能 | 文件 800 行、模块循环依赖、参数 9 个 |
| **SOLID 是否遵守** | ❌ **不能** | "这个类的职责是否单一" 是语义判断 |
| **抽象是否合理** | ❌ **不能** | "该不该抽这一层接口" 只有人能判断 |

**所以**：
- `scripts/design_smell.py` 只能给你**信号**（"这里可能有问题"），
  它**不能**证明代码符合 SOLID。**跑绿了不等于设计好。**
- SOLID 真正的落地方式是**写代码前的四问**（SPEC 模板）+
  **本文件的判据**，由 Agent 在动手时自查。

> 反面模式：把 SOLID 五条全塞进 `AGENTS.md` 让 Agent 背诵。
> 规则越多，遵循率**整体**下降（不只是后面的被忽略）——
> 所以本文件**不进 AGENTS.md**，按需加载。

## 1. SOLID 的可执行判据

不复述教科书定义。每条只给三件事：**违反时长什么样 / 怎么自查 / 常见误用**。

### S · 单一职责（SRP）

**违反的信号**：
- 一个类的描述里出现"和"——"负责解析**和**校验**和**持久化"
- 改一个不相关的需求，被迫改这个文件

**自查问句**："这个类会因为**几个不同角色**的需求而改变？"
（产品经理要改 / 运维要改 / DBA 要改 —— 三个角色 = 三个职责）

**常见误用**：把类拆得过碎，一个 5 行的类配一个 20 行的接口。
**职责 ≠ 步骤**，"读取 → 解析 → 保存"可以是同一职责的三个步骤。

### O · 开闭原则（OCP）

**违反的信号**：每次加新类型都要改同一个 `switch` / `if-elif` 链

**自查问句**："新增一种情况，我需要修改现有代码，还是只新增代码？"

**常见误用**：为了"以后可能扩展"提前造抽象层。
**正确时机**：第二次出现同类分支时再抽（Rule of Three）。

### L · 里氏替换（LSP）

**违反的信号**：
- 子类方法抛 `NotImplementedError`
- 调用方需要 `isinstance` 判断具体类型才能用

**自查问句**："把任何子类换成父类，调用方会坏吗？"

**常见误用**：为了复用代码而继承。**能用组合就别继承。**

### I · 接口隔离（ISP）

**违反的信号**：实现某个接口时，有几个方法只能空实现或抛异常

**自查问句**："实现方有没有被迫依赖它用不到的方法？"

### D · 依赖倒置（DIP）

**违反的信号**：高层模块 `import` 了具体实现（而不是抽象/接口）

**自查问句**："把数据库换成内存实现，业务层要改吗？"

**常见误用**：给每个类都配一个接口。**只为真正的扩展点做抽象。**

## 2. 模式选择：正向清单

遇到什么情况 → 考虑什么模式。

| 情况 | 模式 | 判据 |
|---|---|---|
| 对象创建逻辑复杂（多参数/多步骤/条件分支） | 工厂 / Builder | 构造参数 > 4 个或需要多步 |
| 需要在不改现有类的前提下加行为 | 装饰器 | 行为可叠加、可拆 |
| 一个动作有多种算法，运行时选 | 策略 | 算法族 + 可替换 |
| 状态改变导致行为改变 | 状态机 | 状态 > 3 且行为随状态变 |
| 需要通知多方，且不想耦合 | 观察者 / 事件 | 发布方不该知道订阅方 |
| 接口不兼容但要一起用 | 适配器 | 集成第三方/遗留代码 |
| 复杂子系统要提供简单入口 | 外观（Facade） | 调用方只需 20% 的能力 |
| 多处需要统一处理（校验/日志/权限） | 中间件 / 责任链 | 横切关注点 |

---

## 3. 模式选择：**反向清单**（更重要）

> **过度设计是技术债的主要来源之一**。下面这些比"忘了用模式"更常见、更贵。

| 别用模式，如果… | 理由 |
|---|---|
| 只有**一个**实现类 | 先写实现，第二次出现同类再抽接口（Rule of Three） |
| 需求还不稳定 | 抽象会锁死假设，需求一变抽象就得推翻 |
| 代码总共不到 50 行 | 模式本身的复杂度 > 它解决的问题 |
| 只是为了让代码"看起来专业" | 可读性来自**清晰**，不来自**模式名** |
| 团队没人熟悉这个模式 | 维护成本 > 收益 |

**一句话判据**：**模式的价值 = 它省下的修改次数 × 单次修改成本 − 引入的理解成本。**
算不清就别用。

## 4. 技术债信号的机器检查

```bash
python scripts/design_smell.py src/              # 扫描
python scripts/design_smell.py src/ --json       # 机器可读
```

| 编号 | 信号 | 阈值 | 说明 |
|---|---|---|---|
| SM001 | god-module | 文件 > 500 行 或 顶层定义 > 20 | 多半承担了多个职责 |
| SM002 | circular-import | 存在环 | 依赖方向错了，必然耦合 |
| SM003 | deep-nesting | 缩进 > 4 层 | 可读性差，通常需要提取函数 |
| SM004 | long-params | 参数 > 5 | 考虑引入参数对象 |
| SM005 | god-class | 类方法 > 15 | 职责过多 |

**这些都是 warn，不是 error** —— 每个信号都可能是合理的
（比如生成的代码、配置表）。**看到信号先判断，别无脑改。**

## 5. 自查清单（写代码前 30 秒）

- [ ] 这个模块的职责能用**一句话不含"和"**说清吗？
- [ ] 依赖是单向的吗？有没有环？
- [ ] 我用的模式，能说出"为什么不用更简单的写法"吗？
- [ ] 有没有为"以后可能"的需求预留了抽象？（有 → 多半该删）
- [ ] 新增一种情况时，我要改几处？（> 1 处 → 考虑策略/工厂）
