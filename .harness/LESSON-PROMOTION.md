# 经验晋升协议（LESSON-PROMOTION）

> **解决的问题**：项目里积累了大量**完全可复用的通用教训**，但它们是散的——躺在各自项目的 `lessons.md` 里，**新项目要从零再踩一遍**。
> 本协议定义：**一条经验如何从"本项目踩的坑"，升格为"模板自带的强制规则"。**
>
> **三级通道**：`lessons.md`（项目坑）→ `GLOBAL-LESSONS.md`（通用教训）→ `scripts/` + pre-commit（强制门禁）

---

## 0. 为什么需要它（实测证据）

三个项目的教训是**三种完全不同的形态**，说明"提炼"这个动作**从来没有被规定过**：

| 项目 | 形态 | 体量 | 问题 |
|---|---|---|---|
| UGSimulator | 按领域堆（环境/框架/铁律/流程） | 70K 字符 / 303 行 | 通用与专属**混在一起**，无法整体复用 |
| SylvaPPT | 方法论化（CV-First / 根因修复 / 验证方法论） | 6K 字符 | 组织得好，但**只服务自己** |
| AI投股工作台 | 战争史式（症状→根因→逼出的机制） | 7.7K 字符 | 最有洞察，但**藏在项目报告里** |

**最贵的一批经验根本没人管**：SylvaPPT §3 的「验证方法论」五条（XML 对比 ≠ 视觉验证 / 先复现后修复 / stash 隔离确认回归 / 生产函数实跑 vs 手抄逻辑 / 端到端能跑通 ≠ 正确）——**放进任何项目都成立**，现在却锁在一个项目里。

## 1. 三级通道

```
┌─────────────────────────────────────────────────────────────┐
│ Level 1 · 项目坑                                             │
│   .harness/memory/lessons.md                                │
│   「本项目遇到的、可能是专属的」                                │
│   写法：现象 → 根因 → 正确做法                                 │
└───────────────────────┬─────────────────────────────────────┘
                        │ 晋升条件（满足任一）
                        │ ① 同类坑在 ≥2 个项目出现（有实证）
                        │ ② 命中"通用性信号"（见 §2）
                        │ ③ 用户/AI 主动判断它是通用的
                        ▼
┌─────────────────────────────────────────────────────────────┐
│ Level 2 · 通用教训                                           │
│   .harness/memory/GLOBAL-LESSONS.md   ★模板自带，新项目继承     │
│   「换了项目还成立的工程原则」                                  │
│   写法：一句话原则 + 反例 + 自查 + 来源标记 + 强制等级           │
└───────────────────────┬─────────────────────────────────────┘
                        │ 晋升条件（必须满足全部）
                        │ ① 判定方式明确（能用规则/脚本判定）
                        │ ② 误报率可控（不会吵到人关掉门禁）
                        │ ③ 有真实反例（不是理论上的问题）
                        ▼
┌─────────────────────────────────────────────────────────────┐
│ Level 3 · 强制门禁                                           │
│   scripts/*.py + .githooks/pre-commit.py                    │
│   「机器保证，违反即拦截」                                     │
└─────────────────────────────────────────────────────────────┘
```

## 2. 晋升判定标准

### 2.1 Level 1 → Level 2（项目坑 → 通用教训）

**三个晋升条件（满足任一）**：

| 条件 | 判据 | 例子 |
|---|---|---|
| **跨项目复现** | 同一类坑在两个项目独立出现过 | 「静默吞失败」：SylvaPPT 的裸 `except` + 投股工作台的 `!!FAIL` 统计漏计 |
| **命中通用性信号** | 见下表 | — |
| **主动判断** | 用户或 AI 认定"换个项目照样成立" | 用户直接说"这条通用" |

**通用性信号表**（自检用）：

| 信号 | 通用性 | 说明 |
|---|---|---|
| 提到**通用工具**（git / 包管理器 / CI / 构建缓存 / linter） | ⬆️ 高 | 工具是跨项目的 |
| 提到**通用工程动作**（提交 / 测试 / 验证 / 隔离 / 部署） | ⬆️ 高 | 动作是跨项目的 |
| 提到**验证方法论**（怎么证明"改对了"） | ⬆️ 高 | 方法论跨领域 |
| 提到**反模式**（fail-open / 裸 except / 数据补丁） | ⬆️ 高 | 反模式跨语言 |
| 提到**项目专有实体**（玩家 / PPT 渲染 / 因子 / 某个业务对象） | ⬇️ 低 | 换项目不成立 |
| 提到**特定库版本/特定 SDK 行为** | ⬇️ 低 | 版本一升就废 |
| 提到**本机特定环境**（虚拟层 / 特殊沙箱 / 定制 shim） | ⬇️ 低 | 换机器不成立，应进 `LOCAL-ENV.md` |

**写法要求（Level 2 条目必须包含）**：
1. **一句话原则**（能独立读懂）
2. **反例/坑**（真实发生过的，不是假想）
3. **正确做法**（可操作）
4. **自查句**（一句能自问的话）
5. **来源标记** `[UG]`/`[SY]`/`[AI]`/`[TPL]`/`[峰宝]`
6. **强制等级** 🔴deterministic / 🟡tool / 🔵advisory

### 2.2 Level 2 → Level 3（通用教训 → 强制门禁）

**三个条件必须全部满足**：

| 条件 | 说明 | 反例（不该上强制） |
|---|---|---|
| **判定方式明确** | 能写出确定的检测逻辑 | "修复要根因修复"——无法机器判定 |
| **误报率可控** | 不会大量误报 | "检测绝对路径"若不限范围，会报几百条历史档案 |
| **有真实反例** | 确实发生过 | 理论上可能的问题不值得上门禁 |

**⚠️ 铁律：宁可 advisory，不可吵人**

> **降噪即有效性** —— 若门禁误报多到人把它关掉，**等于没有门禁，还多花了实现成本**。
> 判断标准：**这条规则上线后，人会不会想关掉它？** 答案是"会"就退回 Level 2。

**证据（实测）**：harness_lint 的 L002 若不限作用域，扫全量 `docs/` 产生 **554 条噪音**，真问题被淹没 → 因此引入 `governance/all` 作用域。**这是"降噪"设计的直接出处。**

## 3. 三个项目的经验如何归并（已执行）

### 3.1 归并结果

见 `.harness/memory/GLOBAL-LESSONS.md`（52 条，分 6 类）：

| 类别 | 条数 | 说明 |
|---|---|---|
| M · 元原则 | 1 | **最高层** —— 其他条目的思想出处 |
| V · 验证与测试 | 9 | 全部来自真实 flaky / 假绿 / 静默吞失败 |
| S · 状态与数据 | 11 | 「文本猜状态」谱系 + 只增不减 + 静默兜底 |
| E · 环境与工具链 | 9 | 含本机特有项（已标记） |
| P · 流程与协作 | 20 | 含用户下的 4 条铁律 |
| A · 归档与失效 | 2 | 与决策演进协议配套 |

### 3.2 最高价值条目（用户审核后优先落地）

| 条目 | 为什么最值钱 |
|---|---|
| **M0 结论强度 = 量具强度** | 不是"某个坑"，而是**解释为什么会有坑**的元凶。投股工作台最贵的机制（金标准/DataGate/实盘封存）全部由它逼出 |
| **S1 不要用文本猜状态** | 一个根因的 20 种形态（位置/时长/日结束/专业/关系门槛）—— 一次说透省 20 轮 |
| **P2 假修复三形态** | 数据补丁 / 放宽容差 / 单点特判 —— 一眼识别"假修复" |

### 3.3 建议拆分

- **本机特有项**（vmcache 虚拟层、safe-delete shim）→ 建议单独放 `.harness/memory/LOCAL-ENV.md`，**不跟着模板走**（换机器/别人用会困惑）
- **用户个人铁律**（如"删除操作交给人执行"）→ 标记 `[峰宝]`，模板使用者按需保留

## 4. 操作流程

### 4.1 日常：踩了新坑

```
① 写进 .harness/memory/lessons.md（现象 → 根因 → 正确做法）
② 自问：这条换项目还成立吗？
   ├─ 否 → 留在 lessons.md，结束
   └─ 是 → 按 §2.1 判定，加进 GLOBAL-LESSONS.md（带来源标记）
③ 再自问：能机器判定吗？误报可控吗？
   └─ 都满足 → 升级为 Level 3 脚本规则（见 §4.2）
```

### 4.2 升级为门禁规则

```
① 在 scripts/ 下实现检测函数（新规则 ID，如 G0xx）
② 写进该脚本的规则表与文档
③ **必须做阳性对照**（造一个应当被抓的样本，验证真的抓到）
   —— 这是 M0 元原则的要求，不能只跑一遍"报 0"就信
④ 评估误报：跑一次全量，看是否吵人
   ├─ 吵 → 降级为 warn 或退回 Level 2
   └─ 不吵 → 接入 .githooks/pre-commit.py 拦截
⑤ 在 GLOBAL-LESSONS.md 把该条强制等级改为 🔴
```

### 4.3 模板→项目：新项目继承

新项目由 `new_project.py` 初始化时：
- `GLOBAL-LESSONS.md` **默认继承**（模板自带，直接可用）
- `lessons.md` 是空的（等本项目踩坑）
- 项目可以**追加**自己的通用教训，也可以**反馈**给模板（见 §4.4）

### 4.4 项目→模板：反向回流

新项目踩到的通用坑，应回流到模板。触发条件：
- 同一个坑在新项目又出现了 → **说明模板里的规则不够或没生效** → 反馈模板强化
- 发现了模板里没有的新通用模式 → 按 §4.1 流程加进模板

## 5. 维护

| 时机 | 动作 |
|---|---|
| 每次踩坑 | 按 §4.1 走一遍（3 分钟） |
| 季度 | 合并重复条目；**删掉已失效的**（工具/框架升级后不再适用的坑是负资产） |
| 发现规则被绕过 | 强化检测方式，而不是加人肉检查 |
| 发现门禁被关掉 | 说明误报太多 → 降噪或降级（**先反思规则，别怪人**） |

---

## 6. 一句话总结

> **经验的价值不在于"记下来"，而在于"升格"** —— 记在项目里只能救一个项目，升到模板里能救所有未来的项目，升到脚本里能救所有未来的 Agent。
> 三级通道：**项目坑 → 通用教训 → 强制门禁**。
> 两条纪律：**晋升要有证据**（跨项目复现 / 真实反例）· **上门禁要有节制**（宁可 advisory，不可吵人）。
