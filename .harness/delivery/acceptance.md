# 项目级 Definition of Done

> **与任务级 AC 的区别**（Atlassian 经典区分）：
> - **Acceptance Criteria（任务级）** = *did we build the right thing* —— 这块工作要做成什么样，见 `DoD-TEMPLATE.md`
> - **Definition of Done（项目级，本文件）** = *did we build it to our standard* —— **每个**改动都必须过的质量闸门
>
> Agent 两者都需要。任务级写进任务卡，**项目级写进 `AGENTS.md`** 让 Agent 每次会话都能看到。

---

## 每个改动都必须满足（项目级 DoD）

```
□ 功能在 UI 上真实可走通，不是只能靠 API 调用
□ 数据写入了真实存储，刷新/重开后仍在
□ 新代码已接入主流程调用链（不是孤立模块）
□ 无 TODO / FIXME / 占位符 / NotImplementedError / 空函数体
□ 无假数据、mock 数据、硬编码常量充当真实数据源
□ 错误处理具体：说明预期什么错、为什么、怎么恢复；无 except: pass、无「log 后原样重抛」
□ 至少 1 条错误路径测试 + 1 条边界测试
□ 至少 1 条走真实依赖的集成测试（不全是 mock）
□ 类型检查 / lint / 测试全绿，附真实输出与退出码
□ 密钥与敏感配置在服务端，不在前端产物与仓库
□ 日志/可观测：出问题时能定位（不是靠猜）
□ harness 文件已同步更新（progress / lessons / feature_list / handoff）
```

---

## 不可协商的禁令（违反即打回）

| 禁令 | 替代做法 |
|---|---|
| 不写占位实现 / 空函数体 / `NotImplementedError` | 缺依赖 → 显式报错（`raise` + 说明缺什么） |
| 不用假数据冒充真实数据源 | 接真实数据源；确实没有 → 显式失败并报告 |
| 不写 `except: pass` / 吞异常 | 捕获具体异常 → 记录上下文 → 明确恢复或抛出 |
| 不写「已完成 / 一切正常」这类无证据声明 | 四段式交付报告 |
| 不顺手改超出任务范围的代码 | 发现相邻问题 → 单独报告，不自行修改 |
| 不自行假设需求 | 不确定先问；**先问再做**优于做完再改 |

## 交付报告格式（固定四段）

```
【改了什么】  文件清单 + 每个文件的改动性质
【测了什么】  命令 + 真实输出 + 退出码
【证据】      每条 AC / DoD 项对应一条证据（截图 / DB 查询 / 日志片段）
【剩余不确定性】 UNKNOWN 条目 + 原因 + 建议谁来判断
```

**拒绝接受**：「已实现所有功能，测试全部通过」—— 没有输出、没有证据、没有不确定性清单。

---

## 判定词汇表（审计与自评共用）

每条标准只能判一个状态，**不给部分分**：

| 状态 | 含义 |
|---|---|
| `PASS` | 有**直接证据**证明该条成立 |
| `FAIL` | 有直接证据反驳，或复现出缺陷 |
| `UNKNOWN` | 环境 / 权限 / 依赖导致无法可靠判定 |
| `HUMAN_REVIEW` | 主要靠主观或业务判断 |

**铁律：不得把缺失证据记为 PASS。举证责任在 PASS 这一边。**

## 按项目类型追加

> 项目维护者按实际情况填写，写在下面。示例：

- **Web 应用**：多用户并发不互相覆盖状态；有迁移脚本；有部署路径与回滚方案
- **数据处理**：任务幂等（重跑不重复不丢）；失败可定位到具体记录；有数据质量校验
- **桌面/客户端**：离线可用性与降级策略明确；崩溃可恢复
- **内部工具**：权限隔离；操作可审计
