# 交付层（第六层）

> **本层的存在理由**：前五层保证 Agent「按规范写代码」，但**不保证交付物可用**。
>
> AI 辅助开发最常见的失败形态：
> 计划顺利跑完 → 每个模块都"完成" → 交到你手上却是一个充斥占位符、模块互不相连的简陋 demo。
>
> 本层把「完成」从 Agent 的主观判断，变成流程里的**客观闸门**。

---

## 1. 三类失败与对应防线

| 失败 | 表现 | 为什么会发生 | 本层的防线 |
|---|---|---|---|
| **Incomplete Implementation**<br>（未完成实现） | TODO、占位符、空函数体、假数据、`except: pass` | 没有 Definition of Done → Agent 自己定义"完成"，而它倾向"**看起来**完成" | D1/D2/D3/D4 + `no_placeholder_guard.py` |
| **Wiring Failure**<br>（接线失败） | 模块都写好了，但没接进主流程；handler 注册了从不触发；数据写了没人读 | 计划**横向切模块**，验收**纵向走用户旅程**，两者正交 | D6 + `check_integration.py` + Phase N 接线体检 |
| **Production-Readiness Cliff**<br>（生产就绪悬崖） | 界面漂亮但刷新后数据没了；没有鉴权；密钥在前端；两个用户互相覆盖 | Agent 的奖励信号偏**可见层**（UI/截图/演示），**不可见层**（持久化/鉴权/并发/可观测）被系统性跳过 | Phase N 隐形层检查表 + 独立审计 |

> **记住**：Wiring Failure 的所有子类**都能通过传统测试**。
> handler 从不触发，但 DI 容器里有它 → 测试绿；数据写进了没人读的表 → 契约满足 → 测试绿。
> 所以防线必须是**行为验证**（真的走一遍），不能只靠单测。

---

## 2. 七条交付铁律

### D1 · 完成的定义
一个功能完成 = ① 用户在界面上**能真实走到** ② 数据**真的落库** ③ 有测试证明。三者缺一不可。
> 只写了 API 但 UI 点不到 = **未完成**。只有单测没有集成测试 = **未完成**。

### D2 · 禁止占位实现
不写 TODO / FIXME / 占位符 / `NotImplementedError` / 空函数体。
**缺依赖时显式报错**，不要静默兜底返回默认值。
> 理由：静默兜底会让故障隐形。`return 0` 比 `raise` 危险得多——它让系统在错的状态下继续跑。

### D3 · 禁止假数据冒充真实源
不用 mock / fake / 硬编码常量充当真实数据源。
> 测试里用 mock 可以；**生产路径上绝对不行**。判断标准：这段代码上线后，用户看到的是真实数据吗？

### D4 · 错误处理必须具体
说明预期什么错、为什么、怎么恢复。禁止 `except: pass` 和「log 后原样重抛」。
> 浅层错误处理是占位符最隐蔽的形式：它让代码"看起来"处理了异常，实际什么都没做。

### D5 · 错误路径与边界必测
每个任务至少 1 条错误路径 + 1 条边界条件。
> Agent 是强 happy-path 执行者。你不显式要求 unhappy path，它就不会写。

### D6 · 集成是任务的一部分
新模块交付时必须已接入主流程调用链，不是孤立可用。
> 这一条直接对应「模块没集成」。**把集成写进每个任务的 DoD，而不是留到最后。**

### D7 · 禁止无证据的完成声明
交付报告固定四段：**改了什么 / 测了什么（附真实输出与退出码）/ 每条 AC 的证据 / 剩余不确定性**。
无法验证的标 **UNKNOWN**，**不得记为通过**。
> 「已完成，测试全部通过」不是交付报告，是免责声明。

## 3. 三层门禁

```
┌─ 任务级 ── 每个 task 结束时 ─────────────────────────┐
│  DoD 八项打勾（DoD-TEMPLATE.md）                      │
│  no_placeholder_guard.py 通过                         │
└──────────────────────────────────────────────────────┘
┌─ 集成级 ── 模块完成后 ───────────────────────────────┐
│  check_integration.py：新模块真的被调用了吗           │
│  write-read-reload：数据真的落库了吗                  │
└──────────────────────────────────────────────────────┘
┌─ 收尾级 ── 计划跑完后（Phase N）─────────────────────┐
│  hardening-checklist.md 全项                          │
│  独立 verifier 审计（audit-prompt.md，新会话）        │
│  converge：拿 spec + tasks 对拍代码库，关闭 gap        │
└──────────────────────────────────────────────────────┘
```

**最关键的一条**：收尾级门禁**必须被显式计划**。
大部分人的计划里根本没有"集成"这一项，所以永远不会有人去做。
→ 计划末尾**固定**写 `Phase N: Integration & Hardening`，占 **20–30% 工时预算**。

---

## 4. 三个必做动作（按性价比排序）

| 优先级 | 动作 | 成本 | 直接解决 |
|---|---|---|---|
| **P0** | 每个 task 的 DoD 强制含「UI 能走到」+「≥1 条真实依赖集成测试」+「≥1 条错误路径」 | 每任务多写 5 行 | 占位符 + 未集成 |
| **P0** | 计划末尾固定 `Phase N: Integration & Hardening` | 计划模板改一次 | 整体 demo 化 |
| **P1** | 独立 verifier 审计（**新会话**），四态判定，缺失证据不算 PASS | 每项目一次 | 自证完成 |

---

## 5. 人（你）要先做的两件事

工具替代不了，但成本很低：

1. **派活前先手写 2–3 个锚测试**
   Agent 写的测试和它的实现**共享同一套理解**，盲区会被镜像过去——实现错了，测试也跟着错，全绿。
   你先写的锚测试，它无法用镜像蒙混。

2. **每个任务新开会话**，开头显式加载 spec
   长会话里开头的约定到后面会被遗忘（context rot）。表现为：「第 3 个模块纠正的规矩，第 7 个模块又犯了」。
