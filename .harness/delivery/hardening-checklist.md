# Phase N: Integration & Hardening（收尾清单）

> **为什么必须显式计划这一阶段**：
> 集成不会自然发生。大部分计划的最后一项是"写完最后一个模块"，于是从来没有人去做集成，
> 结果就是——每个模块都对，合起来是个 demo。
>
> **规则**：任何开发计划末尾**固定**写这一段，占 **20–30% 工时预算**。

---

## N-1 · 全链路走查（手动，不是跑测试）

对每一条用户旅程，**手动真的走一遍**。

```
□ 每条核心用户旅程都从入口走到结果（点，不是 curl）
□ 走的时候刻意偏离 happy path：刷新、回退、重复提交、开两个窗口
□ 记录每一处"卡住/没反应/数据没了"的地方
```

> 跑测试通过 ≠ 走得通。测试是脚本的，用户是随机的。

## N-2 · 反占位符扫描

```bash
python scripts/no_placeholder_guard.py <code_root> --fail-on warn
```

```
□ ERROR 全部清零（或已登记进 allowlist 并关联 issue）
□ WARN 逐条确认：是真实债务还是误报
□ 误报写进 allowlist 并在 issue 说明为何合法
```

## N-3 · 接线体检（专治 Wiring Failure）

对每一个**注册了的服务 / handler / 订阅 / 定时任务**，逐个确认：

```
□ 它真的被触发过吗？（查运行日志，不是"应该会"）
□ 它触发后真的产出东西了吗？（查下游表/文件/接口有数据）
□ 产出的数据是**算出来的**还是 fallback 写的？（改输入，看输出是否相应变化）
□ 有消费者在读它写的东西吗？（写了没人读 = 白写）
```

**三类探针**（这三类专抓"看着接好了其实没接"）：

1. **write-read-reload**：造一条数据 → 关闭 → 重开 → 还在吗？
   *不在 = 没有持久化，其他都是演戏。一分钟内分清真系统和漂亮前端。*
2. **让缺失层响亮失败**：指向一个不存在的依赖 / 发畸形输入 / 请求中途断网。
   *真系统会以你能读懂的方式报错；stub 会返回它的固定答案——而"不报错"本身就是信号。*
3. **输出是否真的变化**：改输入，看输出是否相应变化；连续多次运行，输出是否有合理多样性。
   *永远返回同一个值 / 输出收敛到极窄区间 = 什么都没算。*

## N-4 · 隐形层检查表

> 这六项正是"可见层做得好、不可见层被跳过"的塌陷点。每一项缺失都是 Production-Readiness Cliff 的一段。

```
□ 持久化：真实存储 + 迁移脚本
□ 鉴权：真的拦截（用未授权账号实测，不是"代码里写了判断"）
□ 密钥：只在服务端，不在前端产物 / 仓库 / 日志
□ 并发：两个用户同时操作不互相覆盖（实测，不是"应该没问题"）
□ 可观测：出问题时能定位（日志 / 指标 / 链路），不是靠猜
□ 部署：有明确的部署路径 + 回滚方案，能说清怎么知道它是否健康
```

## N-5 · converge 审计（拿 spec 对拍代码库）

```
□ 逐条对照 spec 的功能需求（FR）与成功标准（SC），代码里是否真的有对应实现
□ 逐条对照 tasks.md，是否每条都被验证关闭
□ 对照 CONSTITUTION.md，是否违反了不可协商原则
□ 产出 gap 清单 → **追加**成 gap-closure 任务（tasks.md 是 append-only）→ 关闭后再跑一次
```

> 关键：**实现完 ≠ 完成**。实现完之后还要有一次"拿 spec 对拍代码库"的独立审计。

## N-6 · 独立 verifier 审计

```
□ 在**新会话**里跑（绝不让实现方审自己的作业）
□ 用 delivery/audit-prompt.md
□ 产出 PASS / FAIL / UNKNOWN / HUMAN_REVIEW 四态报告
□ FAIL 与 UNKNOWN 全部有处置：修掉 / 登记 issue / 明确接受
```

---

## 完成判据

**Phase N 结束 = 下面三句都能成立：**

1. 每一条核心用户旅程，我能**手动**从入口走到结果，且数据真的存住了
2. 每一个注册的服务，我有**日志证据**证明它被触发过并产出了真实数据
3. 独立审计的 FAIL 与 UNKNOWN 要么已修，要么已登记 issue 并明确接受

**任一句不成立 → 不许交付。**
