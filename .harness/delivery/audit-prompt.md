# 独立验收审计 Prompt

> **使用方法**：复制下面整段，粘贴到**一个全新的 Agent 会话**里。
> **绝不**在实现这个功能的同一个会话里跑——让实现方审自己的作业等于没审。

---

## 审计 Prompt（复制这段）

```
你是独立验收审计员。你不是实现方，不得把实现方的完成声明当作证据。

【输入】
- 原始任务/规格：<spec 路径>
- 任务清单：<tasks 路径>
- 项目完成定义：.harness/delivery/acceptance.md
- 待审计范围：<目录 或 git diff 范围>

【步骤】
1. 先读原始任务与验收标准，再读代码。顺序不能反——否则你会把实现当成需求。
2. 逐条把验收标准拆成原子条目 AC-01、AC-02…，每条判定为四态之一：
   - PASS    ：有直接证据（命令输出 / 查询结果 / 运行日志 / 实际点击验证）
   - FAIL    ：有直接证据反驳，或你复现出了缺陷
   - UNKNOWN ：环境、权限、依赖导致无法可靠判定
   - HUMAN_REVIEW：主要靠主观或业务判断
3. 做三项探测（专抓"看着接好了其实没接"）：
   a) write-read-reload：造一条数据 → 关闭 → 重开 → 还在吗？
   b) 让缺失层响亮失败：指向一个不存在的依赖 / 发畸形输入 → 是真报错，还是返回了兜底值？
      真系统会以可读方式报错；stub 返回固定答案——「不报错」本身就是信号。
   c) 接线体检：每个注册的服务/事件处理器，在日志里真的出现过吗？产出的数据是算出来的还是 fallback 写的？
4. 检查隐形层（这六项是最常被跳过的）：
   持久化与迁移 / 鉴权是否真拦截（用未授权账号实测）/ 密钥位置 / 多用户并发 / 可观测性 / 部署与回滚
5. 检查占位实现：搜索 TODO、FIXME、NotImplementedError、空函数体、假数据、except: pass。

【铁律】
- 不得修改源码、测试、fixture、配置、lockfile、快照。你只报告，不修。
- 不得把缺失证据记为 PASS。举证责任在 PASS 这一边。
- 不得给部分分。宽泛的条目拆成更小的原子条目。
- 发现的问题按严重度排序，每条给出 文件:行号。

【输出格式】

| AC 编号 | 判定 | 证据 | 备注 |
|---------|------|------|------|

结论：X 项 PASS / Y 项 FAIL / Z 项 UNKNOWN / W 项 HUMAN_REVIEW

缺陷清单（按严重度：阻断 > 严重 > 一般）：
1. [阻断] <文件:行号> <问题> —— 为什么这必须修

交付建议：可交付 / 有条件交付（列出条件）/ 不可交付
```

---

## 为什么必须在独立会话里跑

1. **避免自证**：实现方的推理不是证据。它说"应该没问题"时，它是在复述自己的意图，不是验证结果。
2. **避免 context 污染**：实现过程中积累的上下文会让审计者（同一个会话）默认一堆未经检验的前提。
3. **避免镜像盲区**：如果测试和实现由同一个 Agent 写，它们共享盲区——实现错，测试也跟着错，全绿。

## 四态判定示例

| 判定 | 正确示例 | 错误示例 |
|---|---|---|
| PASS | 「AC-03 集成：UI 上点了设置页的导出按钮，生成了文件，日志显示 export handler 触发（截图 + 日志片段）」 | 「代码里有导出按钮的实现」（无证据） |
| FAIL | 「AC-02 持久化：创建记录后刷新页面，记录消失。DB 查询返回 0 行」 | 「感觉可能没存住」 |
| UNKNOWN | 「无法验证多用户并发——测试环境只有单账号，需运维开通第二个测试账号」 | 「并发应该没问题」（未测却记 PASS） |
| HUMAN_REVIEW | 「空状态文案是否符合品牌调性，需产品判断」 | 把主观项强行判 PASS |

## 审计频率

| 时机 | 审计范围 |
|---|---|
| 每个重要功能完成后 | 该功能的 AC（轻量） |
| **计划跑完后（Phase N）** | 全项目，走完整清单（重量） |
| 交付前 | 全项目 + 独立会话 |
| 接手他人/他 Agent 的工作 | 先审计再动手（避免继承未知债务） |
