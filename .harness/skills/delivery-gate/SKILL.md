# 交付门禁

> **核心立场**：跑完计划 ≠ 可交付。本 skill 是把「完成」从主观判断变成客观闸门的那道门。

## 何时用

- 一个功能/阶段做完，要交付
- 有人问"这能用了吗"
- 你自己怀疑"这好像只是个 demo"
- 计划跑完，要收尾

## 流程

### 第 1 步 · 30 秒快速判定

五问，任一为"否" → 直接判**不可交付**，不要往下走：

1. 每条核心用户旅程，能**手动**从入口点到结果吗（不是 curl）
2. 关掉重开，数据还在吗
3. 新模块在 **UI 上有入口**吗，还是只有单测能调到
4. `no_placeholder_guard.py` 通过吗
5. 每条 AC 能拿出证据吗

### 第 2 步 · 自动检查

```bash
python scripts/init.py                                      # 环境 + 基线
python scripts/no_placeholder_guard.py <code_root> --fail-on warn
python scripts/check_integration.py <code_root>
<类型检查> / <lint> / <测试>
```

四项必须全绿，**贴出真实输出与退出码**（不接受"通过了"这种说法）。

### 第 3 步 · 接线体检（每个注册的服务/handler）

```
□ 真的被触发过吗（查日志）      □ 触发后真的产出东西了吗
□ 产出是算出来的还是 fallback    □ 有消费者在读吗
```

### 第 4 步 · 隐形层六项

持久化与迁移 / 鉴权真拦截（未授权账号实测）/ 密钥位置 / 多用户并发 / 可观测 / 部署与回滚

### 第 5 步 · 独立审计（**新会话**）

复制 `.harness/delivery/audit-prompt.md` 到新会话，产出四态报告。
**铁律**：实现方不得审自己的作业；缺失证据不记 PASS。

## 输出

```
【判定】可交付 / 有条件交付（列出条件）/ 不可交付
【检查记录】第 2-4 步每项的结果（附输出）
【缺陷清单】按 阻断 > 严重 > 一般，每条 文件:行号
【剩余不确定性】UNKNOWN 条目 + 建议谁来判断
```

## 判定标准

| 结论 | 条件 |
|---|---|
| 可交付 | 五问全"是" + 自动检查全绿 + 接线与隐形层通过 + 审计无 FAIL |
| 有条件交付 | 有 UNKNOWN 或一般缺陷，已登记 issue 且明确接受 |
| **不可交付** | 有阻断项：手动走不通 / 数据不落库 / 有占位实现 / 有 FAIL |

## 反模式（自己会犯的错）

| 反模式 | 为什么是错的 |
|---|---|
| 「测试全绿所以能交付」 | 测试可能是镜像的；handler 从不触发也能全绿 |
| 「代码都写完了」 | 写完 ≠ 接上 ≠ 能用 |
| 在同一会话里做审计 | 实现方审自己 = 没审 |
| 跳过手动走查 | 跑测试 ≠ 走得通，用户是随机的不是脚本的 |
