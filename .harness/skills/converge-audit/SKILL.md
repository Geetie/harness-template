# converge 对拍审计

> **核心立场**：实现完 ≠ 完成。计划跑完之后，必须有一次"拿 spec 对拍代码库"的独立审计。
> 这一遍对拍，是把"跑完计划"变成"可交付"的关键一步。

## 何时用

- 开发计划的 tasks 全部标记完成，准备收尾
- 怀疑"计划说做了，但代码里没有"
- 阶段结束，要确认 spec 合规

## 流程

### 第 1 步 · 准备对拍基准

读这四份（顺序不能反，**先读需求再读代码**，否则会把实现当成需求）：
1. `.harness/planning/CONSTITUTION.md`（不可协商原则）
2. spec（功能需求 FR / 成功标准 SC / 验收标准 AC）
3. plan（技术方案 / 数据契约）
4. tasks（任务清单 + 每条的 AC）

### 第 2 步 · 逐条对拍

| 对拍对象 | 问什么 | 产出 |
|---|---|---|
| FR → 代码 | 每条功能需求都有对应实现吗？ | gap 清单 |
| SC → 验证 | 每条成功标准能被验证吗？验证了吗？ | 未验证项 |
| AC → 证据 | 每条验收标准有证据吗（命令输出/查询/日志）？ | 缺证据项 |
| tasks → 关闭 | 每条任务是"验证关闭"还是"自称完成"？ | 虚标项 |
| constitution → 实现 | 有没有违反不可协商原则的实现？ | 违规项 |

### 第 3 步 · 分级

- **CRITICAL**：违反 constitution，或核心用户旅程走不通
- **HIGH**：FR / SC 未被覆盖
- **MEDIUM**：部分覆盖、证据不足、状态虚标
- **LOW**：文档缺失、命名不一致

### 第 4 步 · 追加 gap-closure 任务（**append-only**）

```
## Phase N+1 · Convergence
- [ ] T0xx [CRITICAL] <gap 描述>
      AC：<这条 gap 关闭的判据>
```

**铁律**：tasks 文件只追加，不改已有任务（保可追溯）。已有任务标了完成却发现没做 → 追加一条修复任务，不回去改状态。

### 第 5 步 · 关闭后再跑一次

gap-closure 任务做完后**再跑一次 converge**，确认无残留。有残留就再追加一轮。
直到 converge 报告没有 CRITICAL 与 HIGH。

## 输出

```
【对拍结果】FR x/y 覆盖 · SC x/y 可验证 · tasks x/y 验证关闭
【gap 清单】按 CRITICAL > HIGH > MEDIUM > LOW，每条指向具体文件:行号 或 spec 条目编号
【追加任务】已写入 tasks 的 Phase N+1
【结论】可关闭 / 需再来一轮
```

## 常见误判

| 误判 | 正确做法 |
|---|---|
| 「tasks 都打勾了，所以完成了」 | 打勾是自称，要验证。看得到代码/证据才算 |
| 改已有任务的状态来"对齐" | 改状态 = 篡改历史。追加新任务 |
| 只对照 tasks 不对照 spec | tasks 可能一开始就漏了 spec 的东西。spec 才是基准 |
| 一次 converge 就收工 | gap 关闭后必须再跑，确认没引入新问题 |
