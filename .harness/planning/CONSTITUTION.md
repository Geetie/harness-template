# 项目宪法（CONSTITUTION）

> **定位**：不可协商的原则。所有 spec / plan / tasks 都必须通过 Constitution Check；
> 违反本文件的实现，在 converge 审计中判为 gap，必须关闭。
>
> **来源方法论**：GitHub Spec Kit 的 constitution 机制 —— 用一份文件约束所有 AI 行为，
> 让"规则"从建议变成契约。
>
> **用法**：项目初始化时填好，之后**只增不改**（改需记录理由与日期）。

## 原则（Principle I ~ N）

> 每条格式：**原则名 + 一句话规则 + 违反后果 + 为什么**（"为什么"决定 Agent 如何处理相邻场景）。

### Principle I · 交付完整性
任何功能必须满足"用户在界面上能真实走到 + 数据真的落库 + 有测试证明"三者，缺一不可。
- **违反后果**：视为未完成，不得标记为 completed
- **为什么**：这是本项目的首要失败模式——历史上多次出现"模块都写好了但拼不起来"

### Principle II · 无占位实现
不写 TODO / 占位符 / 桩实现 / 假数据；缺依赖时显式报错。
- **违反后果**：提交被 `no_placeholder_guard.py` 拦截
- **为什么**：占位实现会伪装成完成，把真正的工作推迟到验收阶段

### Principle III · 可验证性
任何完成声明必须附证据（命令输出 / 查询结果 / 日志）。无法验证的标 UNKNOWN，不得记为通过。
- **违反后果**：评审打回
- **为什么**：没有证据的"已完成"是免责声明，不是交付报告

## 如何新增原则

1. **只增不改** —— 修改已有原则必须记录理由与日期（保留历史）
2. **一句话能说清** —— 说不清说明没想清楚
3. **必须写"为什么"** —— 没有理由的原则，Agent 无法推广到相邻场景
4. **同步注册** —— 新增后在 `.harness/MAINTENANCE.md` 与根 `AGENTS.md` 同步指针

## Constitution Check（做计划时必做）

写 plan 或拆 tasks 时，逐条问：

```
□ 这个计划会违反 Principle I（交付完整性）吗？
□ 会引入占位实现吗？（II）
□ 每条完成标准都可验证吗？（III）
□ 技术栈选择符合约束吗？（IV）
□ 有明确的质量闸门吗？（V）
```

任一为"是" → 修改计划，不要指望实现阶段补救。
