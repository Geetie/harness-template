# 测试策略（TEST-STRATEGY）

> **定位**：回答"该写什么测试、怎么分层、怎么汇报、什么时候删"。
> 与 `.harness/CODE-QUALITY.md`（风格）、`design/`（设计）并列，互不重叠。

---

## 0. 先解决一个认知问题

**"测试跑绿了" 和 "测试能抓 bug" 是两件事。**

- 前者只证明测试**执行**了
- 后者才证明测试**验证**了行为

有个一手实证：对 **86,156 个测试补丁**（来自 33,596 个 AI agent 提交的 PR、
2,807 个仓库、5 个编码 agent）的分析发现 —— **80.2% 的补丁含弱或不含显式
验证信号**；强验证率因 agent 而异，从 18%（OpenAI Codex）到 67%（Claude Code）。

> 来源：Banik, Chowdhury & Shamim, *All Smoke, No Alarm: Oracle Signals in
> Agent-Authored Test Code*，**arXiv:2606.18168**（arXiv Comments 字段注明
> Accepted at the 8th IEEE International Conference on Artificial Intelligence
> Testing, 2026）→ https://arxiv.org/abs/2606.18168
>
> 该文局限（作者自己声明，引用时须一并转达）：只分析**语法信号**不分析语义；
> 未覆盖隐式 oracle（崩溃即失败/超时）；判为强信号只说明"存在值比较"，
> **不说明比的是不是正确的属性**。

**实践含义**：覆盖率、测试文件数、绿勾都**不足以**说明测试有效。
所以本模板提供 `scripts/test_audit.py` 做信号级审计 —— 但它是**信号不是判决**。

## 1. 分层：先看你的 bug 从哪来，再谈模型

三种主流模型（都同意一件事：**E2E 要少**）：

| 模型 | 特征 | 适用 | 典型配比（静态/单元/集成/E2E） |
|---|---|---|---|
| **金字塔**（Mike Cohn, 2009） | 单元为主 | 后端服务、库、复杂业务逻辑 | 5% / 60% / 25% / 10% |
| **奖杯**（Kent C. Dodds, 2018） | 集成为主 + 静态分析打底 | 前端/全栈（React、SPA） | 15% / 25% / 45% / 15% |
| **蜂窝**（Spotify） | 集成占压倒多数 | 微服务、事件驱动 | 5% / 30% / 55% / 10% |

### 别争模型，用这个启发式

> **看你最近 20 个线上 bug 来自哪一层，就在那一层加测试。**

（出自软件测试社区对三种模型的对比讨论：三种模型各有适用场景，
按"bug 来源"倒推比按教条选模型有效得多。）

**为什么这比选模型重要**：模型是别人项目的统计规律，你的 bug 分布才是你的。

### 分层约定（本模板）

用 **marker** 或**目录**都可，两者都认：

| 层 | marker | 目录 |
|---|---|---|
| 单元 | `@pytest.mark.unit` | `tests/unit/` |
| 集成 | `@pytest.mark.integration` | `tests/integration/` |
| 端到端 | `@pytest.mark.e2e` | `tests/e2e/` |

```bash
python scripts/test_runner.py --layer unit          # 只跑单元（最快反馈）
python scripts/test_runner.py --layer integration
python scripts/test_runner.py --slow                # 找最慢的测试
```

> **注意**：marker 需在 `pytest.ini` / `pyproject.toml` 里声明<!-- lint-ignore：说明性引用，指项目自己的配置文件 -->
> 并开 `--strict-markers`，否则拼错的 marker 会被静默接受（等于没分层）。

## 2. 别每次都跑全量

```bash
python scripts/test_runner.py            # 默认：只跑受改动影响的（快反馈）
python scripts/test_runner.py --all      # 全量（merge 前 / 每日）
```

选择逻辑会**显式打印**（跑了几个、为什么选它们），不是黑盒。

### ⚠️ 安全规则：TIA 只做选择，不替代全量

测试影响分析（Test Impact Analysis）的通行纪律：

| 时机 | 跑什么 |
|---|---|
| 日常改代码 / PR | 受影响的子集（快） |
| **merge 前 / 每日构建** | **全量**（兜底） |

**为什么必须兜底**：影响映射会漏 —— 动态派发、反射、配置文件、运行时开关
都会绕过静态/覆盖率映射。把 TIA 输出当成"**至少这些**"而不是"**正好这些**"。

### 可选：更精确的选测工具

| 生态 | 工具 |
|---|---|
| Python | [`pytest-testmon`](https://www.testmon.org/)（逐测试覆盖率映射，`pytest --testmon`） |
| JS/TS | `jest --onlyChanged` / `jest --changedSince=main`；Vitest `--changed` |
| 通用 | Bazel（构建图）、Gradle（任务级 up-to-date） |

装了 `pytest-testmon` 后 `test_runner.py` 也能受益（它自己会接管选择）。

## 3. 测试怎么汇报（这是最常缺的一环）

### 三种读者，三种粒度

| 读者 | 想知道 | 不要给他 |
|---|---|---|
| **自己 / 队友** | 跑了哪些、失败原因、怎么复现 | 长篇策略 |
| **产品 / 上级** | 覆盖了什么风险、**没覆盖什么**、能不能发 | 测试函数清单 |
| **未来的接手者** | 为什么这么测、哪些是已知缺口 | 只有绿勾的截图 |

### 汇报模板（可直接抄）

```markdown
## 测试汇报 — <功能/版本>

**范围**：本次测了什么（一句话）
**命令**：`python scripts/test_runner.py --all`（或子集，注明）
**结果**：通过 N / 失败 M（失败项：<列出>）
**分层**：单元 X 个 / 集成 Y 个 / E2E Z 个

### 覆盖了什么风险
- <风险 1> → 由 <测试名> 守护
- <风险 2> → 由 <测试名> 守护

### ⚠️ 没覆盖什么（最重要，别省）
- <缺口 1>：为什么没测（时间/依赖/成本），风险多大
- <缺口 2>：...

### 验证强度
- 弱验证信号占比：X%（`python scripts/test_audit.py`）
- 变异测试分数：X%（若已接入，见 §5）
```

> **为什么"没覆盖什么"最重要**：只报"通过 N 项"等于告诉读者"没事"，
> 而真实情况总是"这些测了、那些没测"。**把缺口写出来才是有效汇报。**

`python scripts/test_runner.py --report` 会自动生成这个骨架。

## 4. 测试的有效性怎么量化

### 4.1 Oracle 信号分级（轻量，随时可跑）

```bash
python scripts/test_audit.py
```

按上引论文的 8 类分类法给每个测试打标：

| 级 | 含义 |
|---|---|
| **W1** | 无断言 —— 只调用不验证 |
| **W2** | 只查存在/非空 |
| **W3** | 只做布尔断言，不比具体值 |
| **W4** | 只验证 mock 被调用 |
| **W5** | 只做快照匹配 |
| **S1** | 值相等/比较 |
| **S2** | 错误、包含或类型检查 |
| **S3** | 两种以上不同强信号 |

**优先修 W1 和 W2** —— 它们最可能是"看起来很勤快、实际什么都没查"。

**别把 W4/W5 一律当坏**：mock 验证在交互测试里是合理的，
快照在 UI 回归里是合理的。论文自己也做了敏感性分析：
把 W4/W5 重新归类为强信号，总体弱信号率变化**不到 1 个百分点**。

### 4.2 变异测试（重武器，证明测试真的能抓 bug）

Oracle 分级只看**语法**；变异测试看**效果** —— 它故意改坏源码
（`>` 改 `>=`、`+` 改 `-`、删 return），看测试会不会红。**没红 = 测试没抓住。**

| 语言 | 工具 | 命令 |
|---|---|---|
| Python | [mutmut](https://github.com/boxed/mutmut) | `mutmut run` / `mutmut results` |
| JS/TS | [Stryker](https://stryker-mutator.io/) | `npx stryker run --incremental` |
| Java | [PIT](https://pitest.org/) | `mvn pitest:mutationCoverage` |

**别一上来全量跑**（很慢）。做法：
1. 选**一个关键模块**（支付、权限、计费）
2. 只对它跑变异
3. 看存活的变异体 → 补测试
4. 逐步扩大

**别追求 100%**：等价变异体（改了但行为相同）杀不掉，
追 100% 会浪费大量时间。**把分数当诊断工具，不是 KPI。**

## 5. 测试的生命周期：什么时候删（这条最常被忽略）

### 问题现象

架构变了、模块删了、接口改了，**测试却依然通过** —— 而且没人删。

### 两个成因（对症下药）

| 成因 | 表现 | 检测 |
|---|---|---|
| **测的是脚手架不是行为** | 只断言"能调用/不为空/状态码存在" | `test_audit.py` 的 W2/W4/W5 |
| **删除不彻底** | 功能名义上删了，依赖还在/代码还在/别处有副本 | 孤儿测试检测 + 删代码后的全量跑 |

### 一个 5 分钟就能做的实验

> **删掉一个功能，跑一遍测试，数一数还有多少测试通过。**
>
> 删掉它守护的对象后**依然通过**的测试，测的不是你以为的东西 ——
> 它断言的是一个"无论功能在不在都成立"的不变量。

这个实验比覆盖率报告信息量大得多。挑你**最自信被覆盖**的功能做。

### 孤儿测试

```bash
python scripts/test_audit.py        # 会列出 import 了不存在模块的测试
```

被测源码已删/改名但测试还在 → 要么补回被测对象，要么**一并删除**。

> **删除纪律**：删被测代码的那个 commit，必须同时处理它的测试 ——
> 这是"改动范围内"的一部分，不是 out of scope。
> 留着通过的孤儿测试是**装饰**，它给人"这块被守着"的错觉。

## 6. 慢测试与不稳定测试

### 找慢测试

```bash
python scripts/test_runner.py --slow          # 最慢的 10 个
pytest --durations=10 --durations-min=1.0     # 官方等价写法
```

**常见元凶**（按修复收益排序）：
1. **fixture 作用域过小** —— 昂贵的 setup 每个测试跑一遍 → 提到 `scope="session"`
   （但可变状态别提到 session，那会造成顺序依赖）
2. **真数据库反复重建** → `pytest --reuse-db --no-migrations`
3. **纯逻辑测试也连 DB** → 只有真需要 DB 的测试加 `@pytest.mark.django_db`
4. **能并行却串行** → `pytest -n auto --dist worksteal`
   （worksteal 对"10ms 单元 + 30s 集成"混合套件效果最好）

### 不稳定测试（flaky）

**不要直接禁用**（禁用 = 失去全部信号）。用**隔离区**：

```bash
pytest -m quarantine --testmon-noselect || true   # 非阻塞车道，仍产出数据
```

**三个护栏（缺一个就变成垃圾场）**：
1. **到期日** —— 隔离的测试必须在 N 天内修好或删除
2. **责任人** —— 每个隔离项有 owner
3. **数量上限** —— 超过阈值就报警

> 最常见失败模式：**隔离区变成墓地** —— 停进去就再没人管，
> 安静地吃掉你的覆盖。所以三个护栏必须进 CI 检查。

## 7. 本模板提供的工具

| 命令 | 作用 | 解决问题 |
|---|---|---|
| `test_runner.py` | 智能选测 / 分层 / 进度 / 汇报 | 每次跑全量、没进度、没分层 |
| `test_runner.py --report` | 生成汇报骨架 | 不会汇报怎么测的 |
| `test_audit.py` | Oracle 信号分级 + 孤儿测试 | 有效性未知、假绿测试 |
| `test_audit.py --fail-on orphan` | 孤儿测试作为门禁 | 测试不删 |

---

## 8. 一句话总结

> **测试的价值不在"跑了多少"，在"能抓住什么"。**
>
> 所以：分层跑（快反馈）+ 全量兜底（防漏）+ 定期量有效性（oracle/变异）
> + 该删就删（不留装饰）。
