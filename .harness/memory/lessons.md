# 坑表（lessons）

> **定位**：记录**会重复犯**的坑与黄金原则。一次性环境问题不记。
> **强制**：代码变更的 commit 若踩了新坑，**必须**更新本文件（`.githooks/pre-commit` 强制必更）。
> **写法**：`现象 → 根因 → 正确做法`。一条一坑，不写长段落。

---

## 格式

```markdown
### YYYY-MM-DD | <简短标题>
- **现象**：<看到了什么>
- **根因**：<为什么会这样>
- **正确做法**：<以后怎么做>
```

---

## 通用黄金原则（跨项目，默认继承）

1. **改代码前先跑一遍基线** —— 不知道"原来是对的"，就无法判断"现在是对的"。
2. **失败要响亮** —— 静默兜底（`return 默认值` / `except: pass`）让系统在错误状态下继续跑，比崩溃危险得多。
3. **不要用自然语言干 linter 的活** —— 代码风格交给工具（eslint / ruff / checkstyle），不要写进 AGENTS.md 占指令预算。
4. **不确定就问，不要自行假设** —— "先问再做"的成本远低于"做完再改"。
5. **改动不超出任务范围** —— 发现相邻问题单独报告，不顺手改（顺手改是回归 bug 的主要来源）。
6. **写文件用工具，不手拼结构化数据** —— JSON/YAML 手拼易损坏；写后必须能 parse。
7. **每个新任务开新会话** —— 长会话开头的约定到后面会被遗忘（context rot）。
