# 交付失败模式库

> **用途**：交付前自查清单。这些模式的共同点是——**代码看着没问题，测试也可能是绿的，但产品是坏的**。
> 命名它们是为了能在评审时一句话指出"这是第几类"，而不是花半小时描述现象。

---

## A. 接线失败（Wiring Failure）

> 模块都写好了、都注册了，但系统没真的连起来。**四类全部能通过传统测试。**

| # | 模式 | 现象 | 要问的一句话 | 怎么发现 |
|---|---|---|---|---|
| A1 | **幽灵订阅**<br>Phantom Subscription | handler 注册了、配置里能查到、DI 容器里有，**但从不触发** | 它在触发吗？ | 查运行日志有没有它的输出；临时加一条启动即打的日志 |
| A2 | **空执行**<br>Empty Execution | 触发了、日志有了、健康检查 HEALTHY，但**没产出有用的东西**（写进了没人读的表） | 它在写吗？ | 查下游表/文件有没有数据；确认有消费者在读 |
| A3 | **伪造输出**<br>Counterfeit Output | 数据按时落地、形状正确、每次值还不一样，但**从来没被计算过**（fallback 一直在写） | 输出是真的吗？ | 改输入看输出是否相应变化；关掉真实计算路径看是否还在产出 |
| A4 | **单调化**<br>Monoculture | 每条单独看都合法，但整体上收敛到一个极窄区间，等于什么都没探索 | 输出有多样性吗？ | 统计一段时间的输出分布；看是否挤在一个窄带 |

**为什么测试抓不到**：单元测试验证函数对不对，契约测试验证接口形状对不对，
但**没有任何一层验证"数据真的从 A 流到了 B 并且被计算过"**。

**防线**：`delivery/hardening-checklist.md` N-3 接线体检 + `scripts/check_integration.py`

## B. 生产就绪悬崖（Production-Readiness Cliff）

> 应用跨过"看起来完成"这条线，远远早于跨过"可投入生产"这条线，而两者之间的距离在真实用户碰到之前是不可见的。

**症状**（出现任意一条即中招）：
- 演示很漂亮，但做了演示之外的事就崩
- **数据不持久**：建了记录，切走再回来没了
- 登录没有意义：要么没有鉴权，要么表单接受任意输入且不拦截任何东西
- "API"是前端跟自己说话：网络请求返回硬编码 fixture，后面没有服务端
- 密钥在前端产物或仓库里
- 两个人同时用会互相覆盖状态
- 没人说得清怎么部署、怎么回滚、怎么判断它是否健康

**为什么会发生**：Agent 的训练与评估奖励**评审者能看见的东西**。
前端几秒可见（截图、演示），后端天生不可见（持久化、授权、并发、可观测）。
**奖励信号偏向可见层 → 模型把可见层做得极好，并学到不可见层是可选的。**

**防线**：`hardening-checklist.md` N-4 隐形层检查表

## C. 未完成实现（Incomplete Implementation）

> 主函数在，happy path 通，但测试缺失、错误处理是桩、边界没处理、与既有服务的接线不存在。
> **Agent 在真正的工程工作开始的地方宣布了胜利。**

**常见形态**：
- `TODO` / `FIXME` / `待实现` / 占位注释
- `NotImplementedError`、空函数体、`pass`
- `return "mock"` / `return fake_data` / 硬编码示例数据
- 错误：`except: pass`、吞异常、`log` 后原样重抛、返回永远不会正确的默认值
- 演示话术：`coming soon` / `演示用` / `先写死` / `暂时返回`

**为什么会发生**：没有 Definition of Done → Agent 用自己的判断定义"完成"，
而那个判断**偏向速度而非完备**。生成占位符比实现错误处理省力得多。

**防线**：D2/D3/D4 铁律 + `scripts/no_placeholder_guard.py`

## D. AI 坏味道（AI Smell）

> 输出中暗示"这是为了看起来合理而生成，而非基于理解生成"的表层模式。
> 判据永远是同一条：**输出的自信 与 输出的证据不匹配。**

| # | 味道 | 识别方法 |
|---|---|---|
| D1 | **捏造的引用** | 命名了符合命名规范但根本不存在的函数/配置项/API 端点 → grep 一下或查文档 |
| D2 | **有对称性无实质** | 三条并列 bullet，交换其中两条含义不变 → 是装饰性结构，不是真区分 |
| D3 | **自信的对冲** | 「业界普遍认为…」「大多数情况下…」→ 试着替换成具体来源，句子就失去主张 |
| D4 | **货物崇拜模式** | 用了 DI / 观察者 / 仓储等模式，但更简单的写法本就能解决 → 结构上存在，不解决任何问题 |
| D5 | **浅层错误处理** | catch 后 log+rethrow / 返回永远不对的默认值 / 静默吞异常 |
| D6 | **镜像测试** ⚠️ | 测试覆盖了实现，但**如果实现有细微而一致的错误，测试照样通过** |
| D7 | **未审直接提交** | 看十秒就开 PR，作者答不出"为什么这么设计" |

**D6 是最危险的一条**：
> "The most dangerous AI smell is code that works perfectly for the tests the agent generated alongside it."

**防线**：派活前自己先手写 2–3 个锚测试——**这些测试 Agent 无法用镜像蒙混**。

## E. 流程类失败

| 模式 | 现象 | 防线 |
|---|---|---|
| **自证完成** | Agent 说"已完成，测试全绿"，而这句话来自亲手做这件事的同一个系统 | 独立 verifier（新会话），四态判定 |
| **完成幻觉** | 报告任务完成时，实际只建了 30–40% 的"真工作" | 项目级 DoD + 收尾审计 |
| **倒退两步** | 修一个 bug → 引入两个 → 修那两个 → 再来三个 | 每次改动跑完整回归；改动超出范围先停 |
| **上下文衰减** | 第 3 个模块纠正的规矩，第 7 个模块又犯了 | 每个任务新开会话，开头显式加载 spec |
| **横向切分塌方** | 每层都"完成"，但从来没有一条路径被真正走通过 | 任务按用户旅程纵向切 + Phase 0 Walking Skeleton |

## 使用方式

**交付前**，对照本文件逐条问：

```
□ A1-A4：每个注册的服务都真的触发并产出真实数据了吗？
□ B：数据持久化 / 鉴权 / 密钥 / 并发 / 可观测 / 部署回滚，六项都在吗？
□ C：还有 TODO、桩、假数据、吞异常吗？
□ D：测试是镜像的吗？引用是捏造的吗？
□ E：是独立完成验证的吗？还是 Agent 自证？
```

**发现新失败模式 → 追加到本文件**（带现象、判据、防线）。这个库应该随项目成长。
