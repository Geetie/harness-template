# Harness 反模式库

> **来源**：2026-09 对三个真实在研项目（UGSimulator / SylvaPPT / AI投股工作台）harness 工程的
> 逐文件批判性审查 + 工具回测实测数据。
>
> **用途**：建 harness 或做季度修剪时对照自查。**每条都标了能不能自动检测**——
> 能自动检测的别靠人眼，人眼审不出漂移。

---

## 一、状态层反模式

### AP-01 · 状态文件无上限膨胀

| | |
|---|---|
| **现象** | `feature_list.json` / `progress.md` 只增不减，越滚越大 |
| **实测** | UGSimulator：`feature_list.json` **192 KB**、`progress.md` **122 KB**；SylvaPPT：59 KB；投股工作台：45 KB |
| **后果** | 192 KB JSON ≈ **50K token**。Agent 光读状态就烧掉半个上下文，且读完抓不住重点——**这是发生在磁盘上的 context rot** |
| **根因** | 只规定了「怎么写」（一行式），没规定「留多久」（生命周期）。且"禁止删条目"规则本身导致无限累积 |
| **检测** | `scripts/state_health.py`（体积/行数/条目数 vs 阈值） |
| **修复** | 按配额归档到 `state/archive/`（归档≠删除，git 与归档文件都保留历史） |

### AP-02 · 第二套状态并存

| | |
|---|---|
| **现象** | 根目录出现 `harness-progress.txt` / `harness-tasks.json` / `*.log` 之类，与 `state/` 三件功能重叠 |
| **实测** | SylvaPPT 同时存在 4 套状态记录：`progress.md` / `session-handoff.md` / `feature_list.json` / `harness-progress.txt`（30 KB） |
| **后果** | 两套状态必然漂移；Agent 不知道该信哪个；每次要多读一份 |
| **检测** | `scripts/state_health.py`（rogue state 检测） |
| **修复** | 状态层**只允许 `state/` 三件**。历史流水归档，其余删除 |

### AP-03 · 状态文件功能重叠

| | |
|---|---|
| **现象** | 多个文件都在记"进度"："一行式索引"和"会话叙事"混在同一个文件里 |
| **实测** | UGSimulator 曾在 `progress.md` 里堆长段落，导致该文件迅速膨胀，后才分离到 `session-handoff.md` |
| **后果** | 职责不清 → 同一件事记两遍 → 两份都更新不及时 |
| **检测** | 人工（看 `progress.md` §10 是否有超过 1 行的记录） |
| **修复** | 严格分工：`progress.md` = **一行式索引**；`session-handoff.md` = **会话摘要**；`feature_list.json` = **功能状态**。三者内容不重复 |

## 二、指令层反模式

### AP-04 · 宪法超长

| | |
|---|---|
| **现象** | `AGENTS.md` 越写越长 |
| **实测** | SylvaPPT **540 行 / 41 KB**；UGSimulator 144 行（规范上限 150，已接近） |
| **后果** | 前沿模型可靠跟随约 **150–200 条指令**，而工具自身系统提示已占约 50 条。
规则越多，遵循率**整体**下降（不是只忽略后面的，是所有的一起变差） |
| **检测** | `scripts/state_health.py`（行数上限） |
| **修复** | **新增规则前先删一条**。知识外推到 skills / memory，宪法只留"做什么 + 去哪儿看" |

### AP-05 · 元规范比宪法还长

| | |
|---|---|
| **现象** | 「如何写 AGENTS.md」的规范文档，长度接近甚至超过 AGENTS.md 本身 |
| **实测** | UGSimulator：`AGENTS-guidelines.md` 147 行 vs 根 `AGENTS.md` 145 行 |
| **后果** | 讽刺且实际有害：规范自己违反了它提倡的"精简"；且 Agent 读模块 AGENTS.md 时可能被拉去读这份元规范，造成 token 泄漏 |
| **检测** | 人工（对比两者行数） |
| **修复** | 元规范是**给人看的**，不要求 Agent 每次读。压缩到"四段式模板 + 五条书写原则"即可 |

### AP-06 · 内联知识而非指针

| | |
|---|---|
| **现象** | 宪法里大段复制了本应在设计文档里的内容（架构图、文件清单、算法说明） |
| **实测** | SylvaPPT `AGENTS.md` §3 内联了 CV-First 完整数据流 + M06 五个文件职责，同时又指向 `docs/CURRENT/02-technical-specs/cv-first-architecture.md` |
| **后果** | **两处必然漂移**，且不知道哪份是真的 |
| **检测** | 人工（看宪法里有没有超过 5 行的代码块/表格，且该内容在别处也有） |
| **修复** | 宪法里只留"做什么 + 去哪儿看"。判断标准：不允许出现"为什么"的长篇解释 |

### AP-07 · 已废止规则表留在宪法里

| | |
|---|---|
| **现象** | 用一张大表记录"已废止的旧规则"，且随架构演进不断增长 |
| **实测** | SylvaPPT `AGENTS.md` §4 有 **17+ 行**已废止规则 |
| **后果** | **这恰恰违反了"stale rules 比缺失更有害"**——一张废止表本身会过期（某条可能又变相关了），且每次读都消耗注意力 |
| **检测** | 人工 |
| **修复** | 废止记录移到 `memory/` 或归档，宪法里只留一行指针。
注意：废止表有存在价值（防止 Agent 从旧代码学到废止做法），**但它不该住在宪法里** |

### AP-08 · 强制阅读清单过长

| | |
|---|---|
| **现象** | `AGENTS.md` 开头列出"任何 Agent 开始工作前必须按顺序阅读 N 个文件" |
| **实测** | SylvaPPT 列了 **8 个**强制文档；另有 4 处文档各列 6 项 |
| **后果** | 一次性全读是 **token 黑洞**；读完之后 context 已充满细节，反而看不清重点 |
| **检测** | `scripts/harness_lint.py` L006 |
| **修复** | 改为**分级加载**：L0 常驻（路由表，~1K token）→ L1 按需（能力卡，单次 ≤2 张）→ L2 深度原文（按需） |

### AP-09 · 跨项目引用污染

| | |
|---|---|
| **现象** | A 项目的治理文档里出现 B 项目的路径 |
| **实测** | UGSimulator `AGENTS.md:95` 写着「先读另一个项目（SylvaPPT）的 docs/README.md」——把别的项目的绝对路径写进了本项目宪法；第 94 行标题是"修改 SylvaPPT 前" |
| **后果** | 项目边界模糊；换机器后该路径失效；新 Agent 困惑于"我到底在改哪个项目" |
| **检测** | `scripts/harness_lint.py` L002（盘符路径） |
| **修复** | 跨项目约定放在**两个项目的公共上位目录**或独立文档，不要写进单个项目的宪法 |

## 三、一致性反模式

### AP-10 · 基线数字多处不一致

| | |
|---|---|
| **现象** | 同一个测试基线在多个文件里被记录，且互不相同 |
| **实测** | UGSimulator 同一基线出现 **4 个值**：architecture.md 写 4630、verification.md 的 §1 写 4614 而 §4 写 4630、AGENTS.md 写 4614、progress.md 写 4017（滞后两批）、test-baseline-maintenance 技能写 4607 |
| **后果** | 之后所有"全绿了吗"的判断都建立在不一致的基准上；更糟的是文档**自己写了警告"下次必须三处对齐"却仍然漂移**——证明 advisory 层的规则不可靠 |
| **检测** | `scripts/harness_lint.py` L003 |
| **修复** | 数字**只留一处权威源**（`init` 脚本），其余一律做指针；或上工具强制比对 |

### AP-11 · 硬编码绝对路径

| | |
|---|---|
| **现象** | 文档里的路径写死盘符（形如 `<盘符>:\<项目名>\...`），而不是仓库相对路径 |
| **实测** | UGSimulator：治理文档里 **48 处**，其中 `AGENTS-guidelines.md` 10 处、`submit-and-harness-sync/SKILL.md` 9 处、`STATE-PROTOCOL.md` 9 处 |
| **后果** | clone 到别的目录/换机器即全部失效；文档无法随项目迁移 |
| **检测** | `scripts/harness_lint.py` L002 |
| **修复** | 一律用**仓库相对路径**；跨文件引用用相对路径或明确的"仓库根 — 路径"格式 |

### AP-12 · 死文件与模糊状态残留

| | |
|---|---|
| **现象** | 0 字节的空标记文件、指向已迁移旧路径的提示文案、"⚠️ 部分有效"这种模糊状态标注 |
| **实测** | SylvaPPT `.harness-active` **0 字节**；UGSimulator `pre-commit` 的提示文案仍引用迁移前的旧路径（上次重构漏改）；SylvaPPT 文档表里 `SKILL.md` 标注"⚠️ 部分有效，但以 docs/CURRENT/ 为准" |
| **后果** | 空文件让 Agent 反复尝试读取并困惑；模糊标注等于没有标注（Agent 不知道能不能信）；hook 文案错会误导修复方向 |
| **检测** | `scripts/state_health.py`（空文件）+ `scripts/harness_lint.py` L001（死引用） |
| **修复** | 重构时**同步扫一遍引用与文案**；模糊标注改为明确的双选一（有效 / 已废弃） |

## 四、用法

### 建 harness 时
对照本表逐条自检，特别是 AP-01 / AP-04 / AP-08（这三条决定 Agent 能不能开工）。

### 季度修剪时

```bash
python scripts/state_health.py          # AP-01 / AP-02 / AP-04
python scripts/harness_lint.py          # AP-08 / AP-09 / AP-10 / AP-11 / AP-12
```

能自动检测的**不要靠人眼**——人眼审不出漂移，这正是 AP-10 的教训。

### 发现新反模式时
追加到本文件，格式：现象 / 实测证据 / 后果 / 检测方式 / 修复。
**带实测证据的条目才有说服力**，不要写"理论上可能会…"。
